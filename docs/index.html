The retriever was reading a fraction of each article

22 August 2026 · Chenjigaram/eu-reg-search

I have been building a search system over EU financial regulation. You ask a question in English and it gives you back the provision that answers it, in Dutch, German or French, with a link to that exact article on EUR-Lex. There is no generation step anywhere in it. The text you get is copied from the source, so there is nothing for a model to make up.

The evaluation set comes from ESMA. Their Q&A documents state a question, answer it, and cite the articles the answer relies on. That gives 141 question-to-article pairs I did not write myself, which matters, because the alternative is generating queries from the same articles you are then scoring against.

The numbers were bad

The first full run scored 0.182 nDCG@10 for the best system. Splitting it by whether the question and the law were in the same language:

Fusing BM25 with the embedder was the best thing in the table, so that became the headline. BM25 was clearly better when the languages matched, the embedder was better across languages, and combining them with reciprocal rank fusion beat either one alone by 19%. I had a tidy explanation for it too: legal terminology is distinctive, so exact matching works well when you can use it.

The fine-tuning was the part that bothered me. I tried it twice. The first attempt was mostly cross-lingual alignment pairs, which teaches the model that two texts are the same provision rather than that a question is answered by one. So I rebuilt the mix, capped the alignment pairs, and swapped the template questions for Inverse Cloze Task pairs. Question-like pairs went from 23% to 74%. Overall nDCG went from 0.147 to 0.146.

I put that down to the corpus. There are 690 trainable articles, which is not much, and the standard story is that below some size you cannot beat general-purpose pretraining. I wrote it up that way and moved on to other things.

I never checked how long the articles were

The model is multilingual-e5-small. Its window is 512 tokens. Somewhere between "0.182 is bad" and "the corpus is too small" I skipped the step where you look at the input.

More than half the articles I was being scored on did not fit. MiFID II Article 4 is the definitions article and the most cited thing in the corpus. It is 4,955 tokens. The embedder was reading the first tenth of it and never saw the rest.

This also explained the thing I had a tidy story for. BM25 does not have a window. It reads the whole article. So when I said BM25 wins on same-language retrieval because legal terms are distinctive, what was actually happening is that one system could see the text and the other could not.

Chunking

The fix is not clever. Split each article into 400-token passages with 80 tokens of overlap, index the passages, and score an article by its best-matching passage. 

def chunk_text(text, tokenizer, size=400, overlap=80):
    ids = tokenizer.encode(text, add_special_tokens=False)
    if len(ids) <= size:
        return [text]
    step = size - overlap
    min_tail = max(1, min(40, size // 4))
    pieces = []
    for start in range(0, len(ids), step):
        window = ids[start:start + size]
        if len(window) < min_tail and pieces:
            break
        pieces.append(tokenizer.decode(window))
        if start + size >= len(ids):
            break
    return pieces

The min_tail guard was originally a flat 40 tokens, which quietly dropped the last chunk of every article when I tested with small window sizes. A test asserting that every token survives chunking caught it. Worth writing that test.

Rerunning everything:

Hybrid, chunked0.2220.3380.183
Dense, chunked0.2190.3050.190
BM25 (unchanged)0.1520.3220.095

The embedder gained 42% overall and 50% cross-lingual. No new parameters, no training, no GPU. It just stopped being fed truncated text. Same-language dense retrieval went from losing to BM25 (0.236 against 0.322) to beating it once fused (0.338).

For a shortlisting tool the more useful number is where the right article lands. Over the 141 same-language questions, the cited article is the top result 18% of the time, in the top five 50% of the time, and in the top ten 57%. Before chunking those were 17%, 40% and 45%. Rank one barely moved. What chunking did was pull the right article into the shortlist rather than to the top of it, which is fine, because the point is to hand someone ten provisions instead of a 335 KB directive.

The part I did not expect

Hybrid scores 0.222 and dense alone scores 0.219. That gap is 0.003, which on 564 queries is about a fifth of a standard error. It is nothing. Both of them clear BM25 by around five and a half standard errors, which is real.

So the hybrid result I had built the whole repo around is gone. Fusion was worth a genuine 19% when the embedder could only read the first 512 tokens of an article. Once it could read all of them, fusion stopped adding anything. It now costs 0.007 cross-lingually, because mixing a 0.095 system into a 0.190 one drags it down.

Reciprocal rank fusion was compensating for a bug. It worked, in the sense that the number went up, and I would not have found the bug by looking at the fused number, because fusing hid it. The thing that exposed it was slicing the results, seeing BM25 and the embedder win different halves, and eventually asking why.

Training had the same problem, only worse

Having found one truncation bug I went looking for others, and the training config had max_seq_length = 192.

75% of articles are longer than that. The median is 386 tokens. So the model was trained on roughly half of a typical provision and then asked at inference to retrieve a 512-token representation of the same thing. The positives it learned and the passages it was scored against were not the same text.

So I fixed it. Training now builds pairs from the same 400-token chunks the index serves, and the training window matches the inference encoder. I expected that to rescue fine-tuning.

It did not.

Same-language retrieval collapses by nearly half, cross-lingual creeps up by 2%. That is the third time today the same shape has appeared, and this time it names the cause: 43% of my training pairs are cross-lingual alignment pairs. The model is being taught that two texts are the same provision, it gets better at exactly that, and it forgets how to match a question to a passage.

Which is what the literature would have told me. Bilingual BSARD is the closest published benchmark to this — statutory article retrieval in Dutch and French — and their fine-tuned models more than double BM25, from 0.20 to 0.45 nDCG@10. They train on roughly 900 labelled question–article pairs. I train on unsupervised proxies, because all 141 of my real pairs are reserved for evaluation.

So the count is: corpus size, guessed, wrong. Truncation, measured, real but not the cause here. Missing supervision, which is the one the comparable paper supports and the one I have not yet tested. Two of my three explanations for this failure were wrong, and the honest version of this section is that I still have not proven the third.

Rerankers, and the same lesson twice

The obvious next move was a cross-encoder reranker. The case for it is arithmetic: the right article is in the top ten 57% of the time but at rank one only 18%, so if a reranker could sort the shortlist perfectly, same-language nDCG would go from 0.338 to 0.581. The information is already retrieved. Only the ordering is wrong.

A small multilingual cross-encoder (mmarco-mMiniLMv2) made it worse: 0.338 down to 0.286 reranking the top ten, and 0.236 reranking the top twenty. Getting worse as the candidate pool grows is the tell — it was promoting wrong articles from ranks 11 to 20 into the top ten. It is trained on short web queries and these are 250-word regulatory questions.

bge-reranker-v2-m3 is the model that should handle long multilingual text, and it is 3.2 seconds per pair on my laptop, which is a 25-hour evaluation. On a Kaggle T4 it took twenty minutes.

Cross-lingual up 9%, same-language down 12%, and applied to everything the two cancel out to nothing. Apply it only where the query language and the article language differ and it is worth about 6%.

That is the second time in this project the answer has been to route rather than blend. Fusion of BM25 and dense retrieval was the first, and it stopped paying once the truncation was fixed. Both effects were invisible in the overall column and only showed up in the slices. If there is one thing I would take from building this, it is that an averaged metric hid a real effect twice in the same system, in the same week, and I nearly shipped the wrong conclusion both times.

What is still wrong with this

  • Two holdouts in the design have no data. Every ESMA question is in English, so the nl→en and de→fr directions never occur, and no PRIIPs RTS citations survived extraction. I promised holdouts the corpus cannot fill.
  • 141 questions cite only 64 distinct articles, so the real diversity is 64.
  • Single seed throughout. I only claim the large gaps.
  • Of 546 Q&A blocks extracted from five documents, only 141 cite an article I can resolve. The PRIIPs Q&A yields 4%, because its answers cite annexes and this indexes articles.
  • Routing by language would score about 0.241 with the reranker, and I have not built it into the system yet — it is measured, not shipped.
  • The supervision theory for the fine-tuning failure is untested. Cross-validating on the 141 ESMA pairs would test it, at the cost of no longer having a clean held-out set.
  • A reranker adds roughly 200 ms per query. The current system answers in 69 ms.

The lesson I would take from this is narrow and slightly embarrassing: I had a plausible explanation for a bad result, and plausible explanations are what stop you from looking. The corpus-size story was never tested. Checking token lengths against the model window is five lines and I should have run it before I ever wrote the word fine-tuning.
